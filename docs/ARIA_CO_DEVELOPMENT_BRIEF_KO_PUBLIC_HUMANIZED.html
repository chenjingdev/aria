Product direction

첸징이 만들려는 것은
“AI용 DAW”가 아니다.

목표는 분명하다. 전문 조작은 AI가 맡고 사람은 귀로 판단할 수 있는 부분을 직접 만진다. 복잡한 DAW의 버튼을 작은 화면에 그대로 옮길 이유는 없다.

02 / 09
REQ–01현재 구현
말로 요청한 내용이 실제 곡 편집으로 이어진다.

LLM이 45개 MCP 도구로 곡·트랙·노트·구조·표현·저장·재생을 다룬다.

완료 기준: 새 곡을 만들고 구간을 재생한 뒤 피드백에 맞춰 같은 곡을 수정할 수 있다.

REQ–02현재 구현
GUI와 AI는 같은 곡을 편집한다.

하나의 state.song과 같은 runOp() 계층을 공유한다.

완료 기준: GUI 변경이 SSE로 반영되고 MCP가 즉시 같은 상태를 읽으며 Undo/자동저장 규칙이 동일하다.

REQ–03부분 구현
비음악인도 들리는 문제를 직접 다룬다.

mute/solo, 트랙 볼륨·팬, velocity, 구간 gain, EQ, reverb, 피아노롤 편집은 있다. 튀는 음량과 타이밍을 한눈에 찾는 시각화는 더 다듬어야 한다.

완료 기준: 사용자가 전문 메뉴를 탐색하지 않고 문제 트랙·구간을 찾고 작은 수정 또는 AI 요청을 할 수 있다.

REQ–04현재 구현
구간 피드백은 AI 작업 큐로 이어진다.

GUI에서 선택 범위와 트랙에 메모를 남기고 AI가 list_feedback로 읽어 수정한 뒤 resolve_feedback로 닫는다.

완료 기준: 피드백의 마디 범위가 구조 편집에도 따라 움직이고 실제 수정 전 임의로 완료되지 않는다.

REQ–05다음 실험
선택한 구간에 여러 후보를 만들고 귀로 고른다.

현재는 곡 전체 A/B 슬롯만 있다. 선택 구간에 서로 다른 후보 3–5개를 만들고 주변 트랙과 끊김 없이 비교한 뒤 한 안을 적용하는 것이 목표다.

검증할 것: 후보가 실제로 서로 다르고 문맥 속 비교가 빠르며 적용 전 원곡이 바뀌지 않는가.

REQ–06현재 구현
장난감 같은 대체음보다 실제 샘플의 표현을 보존한다.

SF2는 SpessaSynth, SFZ는 sfizz가 스테레오·벨로시티 층·라운드로빈·키스위치/CC·드럼 초크를 처리한다.

완료 기준: 요청한 bank/program/key/velocity/articulation이 없으면 원인을 표시하고 곡 상태를 바꾸지 않는다.

REQ–07부분 구현
음악 용어와 감각 언어를 함께 제공한다.

프리셋·주법·믹스 파라미터에는 양쪽 설명이 들어가 있다. 모든 새 기능에서 이 규칙을 일관되게 지키는 디자인 검수가 필요하다.

완료 기준: 정확한 용어, 쉬운 설명, 가능한 경우 A/B 또는 미리듣기가 한 세트다.

REQ–08현재 구현
편집은 되돌릴 수 있고 실패는 곡을 반쯤 바꾸지 않는다.

최대 30단계 Undo/Redo, 자동저장, 곡 라이브러리, SFZ 샘플 대응·bend 채널 사전검사를 갖는다.

완료 기준: 실패한 편집이 곡·Undo·자동저장·GUI 중 일부만 바꾸지 않는다.

REQ–09부분 구현
결과는 Aria JSON·WAV·MIDI·스템으로 옮긴다.

정확한 현재 소리는 WAV가 보존한다. MIDI는 편집 호환을 위한 근사 형식이므로 주법·bend·믹스 손실을 명시하고 위험한 경우 내보내기를 차단한다.

남은 일: volume > 1에서 잘못된 MIDI CC7 값이 생기는 버그를 수정하고 round-trip 정책을 더 분명히 한다.

REQ–10부분 구현
음원 출처와 라이선스를 제품 기능으로 취급한다.

팩 manifest, checksum, 출처, 라이선스, 설치 상태가 있다. 그러나 기본 SoundFont의 클린 설치 절차와 Aria 자체 코드 라이선스는 아직 없다.

완료 기준: 새 개발자가 비공개 파일 복사 없이 합법적인 출처와 검증된 절차로 동일한 상태에 도달한다.

REQ–11현재 구현
작곡 지식은 AI 스킬에서 다듬는다.

aria-compose가 감정·형식·리듬·화성·편곡·믹스·장르·수정 절차를 가르친다. 앱은 실행·검증·렌더를 맡는다.

완료 기준: 음악 규칙이 DSP 코드에 흩어지지 않고 도구 표면과 스킬 문서가 감사 스크립트로 일치한다.

REQ–12다음 실험
음악가의 귀를 재현 가능한 품질 기준으로 바꾼다.

8–16마디 기준곡에서 편성, 주법 전환, groove, climax, tail, 음원별 차이를 같은 범위로 A/B하고 기록한다.

검증할 것: 주관적인 피드백이 코드 회귀 테스트와 충돌하지 않으면서 반복 가능한 acceptance criteria가 되는가.

현재 모델은 화성·프레이즈·에너지 곡선을 별도 객체로 만들지 않는다. 정본은 Song JSON 하나이며 음악적 역할 대부분은 노트·트랙 이름·섹션 레이블로 표현한다.

04 / 09
개념적 Song JSON
{
  title, bpm, timeSig,
  tempoMap: [{ bar, bpm, ramp? }],
  sections: [{ bar, label }],
  tracks: [{
    name, seed, preset,
    volume, pan, mute?, solo?,
    articulation?,
    articulationRegions?: [
      { from, to, articulation }
    ],
    velRange?, reverb?,
    eqLow?, eqMid?, eqHigh?,
    gains?: [{ from, to, db, to_db? }],
    notes: [{
      bar, beat, pitch, dur, vel, bend?
    }]
  }],
  feedback: [{
    id, from_bar, to_bar,
    track?, text, done, ts
  }]
}
좌표
bar는 1부터, 마디 안 beat는 0부터 시작한다.
시간 단위
beat와 dur는 4분음표 단위다. 16분음표는 0.25, 8분음표는 0.5다.
화음
같은 bar/beat에 여러 pitch를 놓는다. 별도 Chord 객체는 없다.
드럼·클립
드럼과 클립에는 프리셋이 제공한 kick, snare, play 같은 피스 ID를 쓴다.
섹션
{bar,label} 이름표다. 섹션 역할·끝·에너지 곡선은 아직 일급 필드가 아니다.
곡 길이
마지막 노트/클립에서 계산하며 최소 8마디다. silence ending용 별도 필드는 없다.
안전
편집 전 검증, 성공 시에만 Undo·자동저장·SSE를 갱신한다.
Schema
명시적 schemaVersion은 없다. 기존 곡 호환은 validateSong()의 기본값·정규화에 의존한다.

음악 언어와 저장 모델을 혼동하지 않는다.

focal, pulse, build, arrive, 코드 심벌, motif, phrase, track role은 aria-compose가 사고하는 언어지만 현재 JSON 필드는 아니다. 이 개념들을 모델에 올릴 때는 AI가 더 잘 작곡하는지, 사람이 더 쉽게 편집하는지부터 검증해야 한다.

권장 공동 작곡 루프

현재 상태 보호

get_song → 열린 피드백 확인 → 의미 있는 고유 이름으로 저장한다.

브리프를 6축으로

장르 어휘, 감정, 움직임, 질감, 서사 곡선, 필수·금지 조건으로 번역한다.

4–8마디 증명

pulse, bass/harmonic floor, 한 가지 정체성, focal gesture로 작은 구간부터 듣는다.

구조 확장

섹션을 붙이고 반복을 복제한 뒤 밀도·음역·편성·리듬 중 필요한 축만 변형한다.

표현 정리

velocity → volume → region gain → register/density → 실제 주법 → 작은 EQ 순으로 본다.

같은 범위 A/B

한 번에 원인 한 층만 바꾸고 전환 전 1–2마디 lead-in을 포함해 비교한다.

피드백 닫기

수정·오디션이 끝난 항목만 완료 처리하고 최종 고유 이름으로 저장한다.

의도에 맞게 내보내기

현재 소리를 보존하면 WAV, DAW 편집 근사면 MIDI, 재믹스면 stems를 고른다.

WAV·MIDI·스템은 무엇이 다른가?
  • Aria Song JSON: 편집 가능성을 가장 완전하게 보존한다.
  • WAV: 선택한 샘플, 주법, pan, EQ, reverb, gain, master sound를 보존한다.
  • MIDI: pitch·onset·duration·velocity·tempo 중심의 교환 형식이다. 정확한 샘플 주법과 믹스는 손실되며 위험한 articulation은 내보내기를 차단한다.
  • Stems: DAW 재믹싱용 트랙 WAV다. 완성 마스터와 동일하지 않으며 현재도 완전한 raw dry stem은 아니다.
Recorded Clip은 왜 일반 노트처럼 자르지 못하나?
Recorded Clip은 원래 연주 전체를 한 번 재생하는 고정 길이 녹음이다. 현재 trim, source offset, time-stretch가 없다. 중간 재생·분할·길이 변경을 허용하면 소리가 조용히 틀어질 수 있어 명시적으로 거부한다.
“후렴이 약하다”를 어떻게 고치나?
전 트랙 볼륨을 일괄 상승시키기 전에 focal register, bass/backbeat 도착, lead-in, 밀도 대비, 주법을 본다. 한 원인 층을 바꾼 뒤 같은 범위를 다시 듣는다. 음악가 공동개발자가 이 진단 순서를 장르별 기준곡으로 구체화하면 큰 가치가 생긴다.

변경 하나의 Definition of Done

01
사용자 시나리오가 한 문장이다.“누가, 어떤 소리를 듣고, 무엇을 고치려는가”가 코드보다 먼저 있다.
02
GUI와 MCP의 의미가 같다.한쪽만 가능한 기능이면 이유를 문서화하고 core 검증을 우회하지 않는다.
03
실패가 곡을 부분 변경하지 않는다.새 mutation은 Undo·autosave·SSE·rollback 계약을 통과한다.
04
정확한 용어와 쉬운 설명이 함께 있다.새 음악 기능은 UI·MCP schema·skill capability에서 같은 뜻을 쓴다.
05
같은 구간의 귀 검증이 있다.원본과 변경본을 동일 범위·같은 조건에서 A/B하고 결과를 기록한다.
06
자동 검사가 재현된다.관련 회귀 테스트, 스킬 감사, 전체 npm test가 통과하고 skip을 구분한다.
07
음원 출처와 손실을 숨기지 않는다.fallback, MIDI 근사, 라이선스, 플랫폼 한계를 사용자에게 드러낸다.
08
원래 곡으로 돌아갈 수 있다.넓은 실험 전 고유 이름 저장, 작은 편집, Undo/Redo 또는 A/B 경로가 있다.

첫 기여로는 “클린 머신 온보딩 + 8마디 음악 품질 체크”를 권한다. 시스템 전체를 안전하게 훑으면서 실제 소리가 맞는지 확인하는 과제다. 음악가의 귀와 개발 역량을 함께 쓰기 좋다.

Glossary & source trail

같은 단어로 이야기하기.

전문 용어를 없애기보다 쉬운 뜻을 바로 붙인다. 세부 구현이 바뀌면 아래 저장소 문서와 실제 코드가 최종 근거다.

MCP
LLM이 앱의 도구를 발견하고 호출하는 연결 규약.
Song JSON
Aria가 편집 가능한 곡의 정본으로 삼는 구조화 데이터.
Velocity
한 음을 얼마나 세게 연주하는지. 샘플의 강약 층과 음색에도 영향을 준다.
Articulation
스타카토·피치카토처럼 실제 발음과 연주 방식이 달라지는 주법.
Round robin
같은 음을 반복할 때 다른 녹음 take를 순환해 기계적인 반복을 줄이는 규칙.
Keyswitch / CC
샘플러에 주법이나 상태를 전달하는 MIDI 제어 방식.
SF2 / SoundFont
샘플과 악기 매핑을 묶은 포맷. Aria에서는 SpessaSynth가 재생한다.
SFZ
텍스트 악기 정의와 오디오 파일을 조합한 개방형 샘플 포맷. sfizz가 재생한다.
Stem
DAW에서 다시 섞기 위한 트랙별 오디오 파일. 완성 믹스와는 다르다.
LUFS
사람이 느끼는 음량에 가까운 비교 지표. 음악성이나 납품 true-peak 보증은 아니다.
Fallback
없는 자산 대신 비슷한 것을 조용히 쓰는 자동 대체. Aria의 음원 경로에서는 금지한다.
True legato
앞 음에서 다음 음으로 넘어가는 실제 전이 녹음을 재생하는 레가토.
